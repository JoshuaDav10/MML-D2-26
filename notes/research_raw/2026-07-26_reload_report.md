# Matching ROCK_NEO.EXE: SN-Patched GCC 2.7.2 Sources, Reload Live-Range-Split Artifacts, and Other MML Decomps

## TL;DR

- **No public, canonical SN Systems 2.7.2.SN32.3.7 *source* tree exists as such** — but the decomp community has a *reconstruction*: `decompals/old-gcc`’s `2.7.2-cdk` target, which builds from a hosted tarball (`cdk-gcc-b18`) and reproduces the SN “compiled by” banner. Critically for your problem, **it does not patch the register allocator or reload passes** (`local-alloc.c`, `global.c`, `reload.c`, `reload1.c` are stock FSF 2.7.2); only `config/mips/mips.h` plus build-system/PSX behavior patches are applied. So your reload artifact is *stock gcc 2.7.2 reload behavior*, not an SN-specific one — meaning FSF 2.7.2 internals reasoning applies directly.
- **Your two symptoms are known, documented, and often unreachable-by-source.** The reg-to-reg live-range-split copy and the phantom (never-accessed) spill slot are exactly the class of artifact that decomp-permuter is explicitly weak at (stack diffs) and that projects routinely resolve either by register-pressure manipulation (extra locals, duplicated expressions defeating GVN, call-boundary pressure) or by declaring the function permanent `NONMATCHING`/hand-asm. No one has published a clean “force the extra move” idiom that is guaranteed.
- **Another MML decomp beyond ChrisNonyminus/mml1 and your fork does not appear to exist — but something better does: Capcom shipped uncompiled C source inside the game itself.** The Cutting Room Floor documents that the Japanese PS1 and PSP builds contain leftover uncompiled source (including references to `moji.c` / `MojiTaskExec2` and `Moji_flag`) embedded in `ST1E.BIN`. This is a primary-source goldmine for the moji/text renderer you are chasing at 0x80053B40.

### Question 2 — Prior art on the reload live-range-split copy and phantom stack slot: FOUND (well-trodden, rarely fully “solved”)

- **decomp-permuter (simonlindholm/decomp-permuter)** is the primary tool. Its README states, verbatim: “0 means the function matches fully. Stack positions are ignored unless `--stack-diffs` is passed (but beware that the permuter is currently quite bad at resolving stack differences),” and that it is “generally best towards the end, when mostly regalloc changes remain.” Your phantom 8-byte slot falls squarely into that documented weakness.
- **The n64decomp/oot “-O2 decompilation (for IDO 5.3)” guide** (<https://github.com/n64decomp/oot/blob/master/docs/guides/-O2%20decompilation%20(for%20IDO%205.3).md>) documents two directly relevant idioms even though it targets IDO. On forcing regalloc via expression duplication: “The compiler has a Global Value Numbering pass which deduplicates expressions. However, the act of deduplication affects register allocation. Thus one can sometimes force different regalloc by duplicating various expressions.” On phantom stack slots (verbatim): “the optimizer can then move some variables into registers, leaving slots empty. If an explicitly declared stack variable is unused or placed in a register, and it is last in the declaration order, it won’t affect sp.” This is the standard lever for *creating* an otherwise-untouched stack reservation — declare extra locals and manipulate their placement/order.
- **PSY-Q-specific permuter forks exist:** `FoxdieTeam/decomp-permuter-psyq` (confirmed live: “Randomly permute C files to better match a target binary,” a PSY-Q-adapted fork) and `twevs/decomp-permuter-psyq` — more likely to model 2.7.2 regalloc quirks than the mainline permuter.
- **Register-pressure manipulation across a call boundary** is the canonical way to force a caller-saved→callee-saved copy: because the value must survive a call, gcc keeps it live in a callee-saved register but first materializes it in a scratch. Introducing/relocating a function call so the pointer is live across it is the mechanism most likely to reproduce your `lw $v0 … addu $s1,$v0,$zero` split, rather than any spelling of `b = a` (which, as you proved via `combine_regs`, cse always collapses).
- **Verdict on reachability:** Multiple mature PSX projects using this compiler generation — sotn-decomp (Xeeynamo), Legend of Mana (celophi/lom-decomp), open-spyro (theMagicalKarp), esa (mkst) — carry permanent `NONMATCHING`/`INCLUDE_ASM` functions precisely because some regalloc/reload episodes are not reproducible from C. Declaring 0x80053B40 a permanent asm function is an accepted, precedented outcome if pressure manipulation fails. No public writeup claims a *general* C idiom that deterministically forces a reload live-range-split copy or a phantom spill slot; these remain trial-and-error via the permuter plus hand pressure-tuning.

## Details

**Compiler provenance and why it matters for you.** Your binary reporting `GNU C 2.7.2.SN32.3.7 Build 0001` with a `/home/aaron/sn-2.7.2` build path is a host recompile of a reconstructed SN 2.7.2 tree. The decompals `2.7.2-cdk` target is the public analogue of that reconstruction. The decisive fact is that the reconstruction leaves the middle-end untouched: reload and register allocation are stock FSF gcc 2.7.2. That means (a) your `local-alloc.c:combine_regs` analysis is valid against the real behavior, and (b) any FSF gcc 2.7.2 source you can obtain (ftp.gnu.org old-gnu, or the decompals build) is a faithful reference for reload1.c / reload.c reasoning. The SN customization that does matter is confined to the assembler-interface / MIPS backend header and is handled downstream by maspsx and ASPSX quirks (li/move expansion, `$at` usage,  jumps-to-nop), not by codegen register decisions.

**The reload inheritance mechanism.** Your two symptoms being one episode is consistent with gcc 2.7.2 reload behavior: reload allocates spill slots, then register inheritance in reload1.c reuses an already-loaded value in a register instead of reloading from the slot, leaving the slot allocated but never accessed — the “phantom 8 bytes.” Simultaneously, the value that must survive a call is inherited into a callee-saved register via a reg-to-reg move that cse cannot delete because the pseudo is live across the call. No public matching-decomp writeup isolates reload inheritance by name with a reproducible C idiom; the practical community knowledge is the pressure-manipulation levers above plus the permuter.

**Practical levers, ranked by precedent:**

1. Introduce/move a real function call so the pointer is live across it (forces callee-saved retention with a materializing scratch move).
1. Add extra local variables (and take their address, or leave one unused and last in declaration order) to grow the frame and create/retain the untouched slot, per the OOT stack-slot note.
1. Duplicate an expression to perturb GVN/cse and shift regalloc.
1. Run `decomp-permuter` (ideally a psyq fork) with `--stack-diffs`, accepting it is weak here.
1. If all fail, accept `INCLUDE_ASM`/`NONMATCHING` as sotn/lom/spyro do.
